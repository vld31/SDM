# Pico 2 W records RP2040 through SWD alone

**Approach proposition, Universal Black Box (Group 7).** A Raspberry Pi Pico 2 W can work as a non-intrusive flight recorder for an unmodified RP2040 target. It needs nothing but the SWD wires and the target's ELF file, because the RP2040's debug port reads memory and peripherals while both cores keep running, and the CPU always wins bus arbitration against the debugger ([RP2040 datasheet](https://cdn.sparkfun.com/assets/b/2/6/7/2/rp2040-datasheet.pdf)). We recommend the following architecture. A PC tool turns the PlatformIO ELF (DWARF) and the RP2040 SVD into a compact capture manifest. The probe runs a PIO-based SWD engine adapted from Raspberry Pi's MIT-licensed debugprobe ([raspberrypi/debugprobe](https://github.com/raspberrypi/debugprobe)). It polls globals, allowlisted peripheral registers, DHCSR and the DWT PC sample register into a RAM pre-trigger ring, and on a fault or trigger it commits the window plus a RAM snapshot to a CRC-protected flash ring. A Python decoder then produces a JSON-lines event log, a readable text trail and a Perfetto/VCD timeline. Two of the four capture goals carry a catch. Core registers (PC/SP/LR/xPSR) can be read only while the core is halted, so the box halts only on a fault, and every halt freezes the RP2040 TIMER and watchdog by default ([RP2040 §4.6](https://xiao-seeed-rp2040-renode.readthedocs.io/en/latest/specification/rp2040-datasheet/06_chapter_4_peripherals/06_4.6_timer/), [pico-sdk watchdog.h](https://the-tk.com/cgit/kutter/tree/lib/pico-sdk/rp2040/hardware/structs/watchdog.h)). Several peripheral registers change state when read, so peripherals must be read from an allowlist, never swept. Our estimate is that a 10 MHz SWD clock (safe on jumper wires) supports about **1 kHz snapshots of ~50 variables plus 100 Hz peripheral frames**, and a full 264 KB RAM dump takes roughly half a second. These figures are derived, not measured, and Phase 0 of the plan exists to measure them.

**Reading convention.** A statement with an inline source link is a sourced fact. A statement marked **[Estimate]** or **[Inference]** is our own engineering reasoning or arithmetic and must be checked on hardware. Where the research notes disagree, we say so and say which source we trust.

## Four capture goals, two wires, zero target changes

The black box has to answer one question after the fact: *what was the PicoBricks board doing, and why did it stop?* It does that through four capture classes. The first is **named global variables**, resolved from ELF/DWARF to absolute addresses. The second is **core state and faults**: PC/SP/LR/xPSR, HardFault, lockup and resets. The third is **peripheral registers** (GPIO, ADC, PWM, UART), decoded to field names via the SVD. The fourth is **RAM snapshots** taken on a trigger. Everything is recorded on the probe flight-recorder style and turned into a human-readable trail and timeline later, on a PC.

The constraint that shapes every decision is that the only inputs are **SWD (SWCLK/SWDIO/GND) and the ELF file**. That rules out all instrumented approaches. SEGGER RTT and SystemView need the target to link and write a ring buffer, which yapicoprobe exploits by locating the RTT control block in target RAM ([yapicoprobe](https://www.Github.com/rgrr/yapicoprobe)). SWO/ITM trace tools such as MCUViewer's Trace Viewer require Cortex-M3/M4/M7/M33 cores, not the RP2040's M0+ ([MCUViewer](https://github.com/klonyyy/MCUViewer)). What remains is the technique that every no-instrumentation tool already uses: SEGGER J-Scope in HSS mode, MCUViewer's Variable Viewer and PicoReg 2 all take addresses from the ELF and do periodic background reads while the core runs ([SEGGER KB: HSS](https://kb.segger.com/HSS), [SEGGER KB: J-Scope](https://kb.segger.com/J-Scope), [PicoReg 2](https://iosoft.blog/picoreg2)). Our contribution is to move that loop off the PC and onto a standalone probe with its own storage, triggers and fault capture, and to add an offline decoder that writes the result up as a story rather than a plot.

A note on PlatformIO: the "unmodified firmware" goal collides with the fact that PlatformIO's default **release build "does not contain symbolic debug information"**, while the debug build uses "no optimization" ([PlatformIO build configurations](https://docs.platformio.org/en/latest/projectconf/build_configurations.html)). Switching to `build_type = debug` would therefore change the code being observed. **[Inference]** The right compromise is to keep the release optimisation level and add `-g` to `build_flags`, so DWARF is emitted without changing generated code, and to prove the code is unchanged by comparing the `.text` section hash of builds with and without `-g`. This is listed as an open question below.

## Non-intrusive on RP2040 means passive reads, rare halts, forbidden registers

### Background reads cost the firmware almost nothing

On the RP2040's Cortex-M0+ cores, "processor and debug accesses share the external AHB-Lite interface" and the processor has priority (§2.4.2.6, §2.4.3.4); the debugger can even reach the per-core SIO block (§2.4.2.7) ([RP2040 datasheet](https://cdn.sparkfun.com/assets/b/2/6/7/2/rp2040-datasheet.pdf)). Arm describes such debug access as non-intrusive on a zero-wait-state system ([Cortex-M0 TRM](https://documentation-service.arm.com/static/5e8e294afd977155116a6a5b)), and its M0+ errata notice confirms that "a debugger can perform memory accesses through the Cortex-M0+ processor bus matrix while the processor is running" ([ARM-EPM-018879](https://documentation-service.arm.com/static/5fa29ee0b209f547eebd35c2)). The debugger is the one that waits, not the core. There is one subtlety. The bus fabric uses round-robin tie-breaks between equal-priority masters that hit the same slave in the same cycle, and BUSCTRL has no separate debug master because debug traffic enters through a core's port ([RP2040 datasheet](https://cdn.sparkfun.com/assets/b/2/6/7/2/rp2040-datasheet.pdf)). **[Inference]** A debug read can therefore delay DMA or the *other* core by about one bus cycle if they collide on the same SRAM bank or APB bridge. At SWD rates that happens at most once every few microseconds. That is "very low", not "zero", and the report should say so honestly.

Two M0+ errata touch this design. Erratum 777019 can push the core into lockup when a waited debugger access coincides with a pending NMI while running at HardFault priority. Erratum 789069 can corrupt simultaneous *debugger writes* to the I/O-port region. Both are listed as present in r0p0 ([ARM-EPM-018879](https://documentation-service.arm.com/static/5fa29ee0b209f547eebd35c2)), and the RP2040 CPUID reports REVISION 0x1, i.e. r0p1 ([RP2040 datasheet](https://cdn.sparkfun.com/assets/b/2/6/7/2/rp2040-datasheet.pdf)). **[Inference]** RP2040 is therefore probably unaffected, but the errata table is ambiguous about r0p1. The design rule costs nothing: never write to SIO (0xD0000000), and note that the NMI trigger is unused unless the firmware configures it.

### Some registers change when you look at them

A recorder that blindly dumps peripheral space will break the firmware it observes. Several read side effects are sourced. Reading SIO `FIFO_RD` pops the inter-core FIFO and can set a sticky ROE flag. Reading `TIMELR` latches `TIMEHR` until it is read, which would corrupt the firmware's own latched time read, whereas `TIMERAWH/TIMERAWL` "read the raw time without any latching" ([RP2040 datasheet](https://cdn.sparkfun.com/assets/b/2/6/7/2/rp2040-datasheet.pdf), [RP2040 §4.6](https://xiao-seeed-rp2040-renode.readthedocs.io/en/latest/specification/rp2040-datasheet/06_chapter_4_peripherals/06_4.6_timer/)). DHCSR's `S_RESET_ST` and `S_RETIRE_ST` are clear-on-read sticky bits ([TI SWCU193](https://ti.com/document-viewer/lit/html/SWCU193/GUID-20221130-SS0T-LTTD-HKTS-BP9GRCRJHXBH)). That is harmless with a single probe, but only one agent may poll them. The CMSIS-SVD format has a `readAction` attribute (`clear`, `set`, `modify`, `modifyExternal`) for exactly this ([svd-rs ReadAction](https://docs.rs/svd-rs/0.14.8/svd_rs/readaction/enum.ReadAction.html)). **[Inference]** Other pop-on-read registers come from general PL011/DesignWare knowledge and still need checking against datasheet chapter 4: UART `UARTDR`, the ADC `FIFO`, PIO `RXFn`, SPI `SSPDR`, and the I2C `IC_CLR_*` clear-on-read registers. Vendor SVDs often under-use `readAction`, so the manifest generator must combine SVD flags with a hand-curated denylist and, better, only read registers on an explicit allowlist. **[Inference]** Reading XIP flash at 0x10000000 through the debugger can evict the core's cache lines. Code bytes should come from the ELF, never from the target.

### Halting freezes time

Core registers (R0–R12, SP, LR, PC, xPSR) are only accessible through DCRSR/DCRDR while the core is halted ([Cortex-M0 TRM](https://documentation-service.arm.com/static/5e8e294afd977155116a6a5b), [TI SWCU193](https://ti.com/document-viewer/lit/html/SWCU193/GUID-20221130-SS0T-LTTD-HKTS-BP9GRCRJHXBH)). On RP2040 a halt has system-wide effects. `TIMER.DBGPAUSE` bits DBG0/DBG1 reset to 1, so the 1 µs timer stops whenever either core is in debug mode ([RP2040 §4.6](https://xiao-seeed-rp2040-renode.readthedocs.io/en/latest/specification/rp2040-datasheet/06_chapter_4_peripherals/06_4.6_timer/)). `WATCHDOG.CTRL` likewise resets with `PAUSE_DBG0`, `PAUSE_DBG1` and `PAUSE_JTAG` set, the last pausing the watchdog "when JTAG is accessing the bus fabric" ([pico-sdk watchdog.h](https://the-tk.com/cgit/kutter/tree/lib/pico-sdk/rp2040/hardware/structs/watchdog.h)). SysTick also runs from the same 1 µs tick ([RP2040 datasheet](https://cdn.sparkfun.com/assets/b/2/6/7/2/rp2040-datasheet.pdf)). **[Inference]** A halt therefore drops target time, lets interrupts and peripheral events pile up, and postpones any watchdog reboot the firmware relied on. That is acceptable post-mortem, unacceptable as a periodic sampling method. Whether plain SWD AHB-AP traffic counts as "JTAG" for `PAUSE_JTAG` is unknown, and if it does, heavy polling would slightly stretch watchdog timeouts.

The RP2040 offers one escape from halting. Its M0+ cores implement a **Program Counter Sampling Register "for non-intrusive profiling"** (§2.4.2.4) ([RP2040 datasheet](https://cdn.sparkfun.com/assets/b/2/6/7/2/rp2040-datasheet.pdf)). It reads as 0xFFFFFFFF unless `DEMCR.DWTENA` is set ([TI SWCU193](https://ti.com/document-viewer/lit/html/SWCU193/GUID-20221130-SS0T-LTTD-HKTS-BP9GRCRJHXBH)). One research note claimed, from unverified general knowledge, that the M0+ lacks PCSR. The RP2040 datasheet says otherwise, and we trust the datasheet. The cores have no MTB, no cycle counter and no ITM/ETM ([RP2040 datasheet](https://cdn.sparkfun.com/assets/b/2/6/7/2/rp2040-datasheet.pdf)), so a statistical PC trace is the only continuous view of execution available. **[Inference]** SP and LR cannot be sampled without a halt. Stack usage can still be estimated without halting by scanning the stack region (known from ELF linker symbols) for a high-water mark.

### A four-level intrusiveness ladder

We propose defining "non-intrusive" operationally, as levels the box declares in every recording header:

| Level | What the probe does | Effect on target | Used for |
|---|---|---|---|
| L0 passive read | AHB-AP reads of SRAM, allowlisted peripherals, DHCSR, DWT_PCSR, TIMERAW* | No stall of the reading core (CPU has priority); ~1 bus cycle possible to DMA/other core **[Inference]** | All periodic sampling |
| L1 debug config write | Set `DEMCR.DWTENA`, `DHCSR.C_DEBUGEN` (key 0xA05F), `DEMCR.VC_HARDERR` | No effect until an event fires; with C_DEBUGEN set, `BKPT` halts instead of escalating to HardFault ([TI SWCU193](https://ti.com/document-viewer/lit/html/SWCU193/GUID-20221130-SS0T-LTTD-HKTS-BP9GRCRJHXBH)) | Arming PC sampling and fault catch |
| L2 halt | Halt-read-resume on fault or explicit trigger | TIMER and watchdog frozen; IRQs delayed | Registers + stacked frame + RAM snapshot |
| Forbidden | Rescue DP (`0xF1002927`), any target memory writes, SIO writes, `AIRCR.SYSRESETREQ`, side-effect reads | Rescue DP CDBGPWRUPREQ hard-resets the chip ([RP2040 datasheet](https://cdn.sparkfun.com/assets/b/2/6/7/2/rp2040-datasheet.pdf)) | Never |

The default mode should be L0+L1, with L2 only on fault. A "strict" mode (L0 only) is worth keeping for demonstration, because it shows the honest trade-off: strict mode can detect lockup and resets but cannot recover core registers.

## Architecture: the PC prepares, the probe records, the PC explains

The system splits into four parts. Only one of them runs on the probe.

**Probe firmware (Pico 2 W).** The SWD physical layer is the debugprobe PIO program. Each TX FIFO word is a command (bit count, direction, jump target) or data, and SWCLK is side-set at 4 PIO cycles per period ([raspberrypi/debugprobe](https://github.com/raspberrypi/debugprobe)). debugprobe builds officially for `PICO_BOARD=pico2`, `PICO_PLATFORM=rp2350` ([debugprobe README](https://pigweed.googlesource.com/third_party/github/raspberrypi/debugprobe/+show/refs/heads/main/README.md)). We keep `probe.pio` and the bit-level read/write helpers and drop TinyUSB, FreeRTOS and the CMSIS-DAP parser. On top sits a thin ADIv5 layer: line reset, TARGETSEL, DPIDR, CTRL/STAT power-up, AHB-AP CSW (32-bit, single auto-increment), TAR/DRW, and WAIT/FAULT/sticky-error handling. RP2040 needs SWD multidrop: core0's DP is `0x01002927` and core1's is `0x11002927` ([RP2040 datasheet](https://cdn.sparkfun.com/assets/b/2/6/7/2/rp2040-datasheet.pdf)). probe-rs's `multidrop_raw.rs` is a working reference for raw selection ([probe-rs](https://docs.rs/crate/probe-rs/latest/source/examples/multidrop_raw.rs)). Shared SRAM and peripherals look the same through either core's AP; only SIO and the SCS (0xE000xxxx) are per-core ([RP2040 datasheet](https://cdn.sparkfun.com/assets/b/2/6/7/2/rp2040-datasheet.pdf)). **[Inference]** The sampler therefore lives on core0's DP and switches to core1 only briefly, to read its DHCSR. Block reads must re-write TAR at every 1 KB boundary, because ADI only guarantees 10 bits of TAR auto-increment. Packed 8/16-bit transfers should be avoided, as OpenOCD avoids them because they "seem to sometimes return garbage" ([OpenOCD arm_adi_v5.c](https://openocd.org/doc/doxygen/html/arm__adi__v5_8c_source.html)).

**[Inference]** On the probe, core 0 runs the sampling loop from SRAM (`__not_in_flash_func`), so flash writes cannot stall it. Core 1 owns encoding, the flash/SD writer and the USB/Wi-Fi link, and a lock-free SRAM ring connects the two. Flash erase and program need `flash_safe_execute`, which locks out the other core and disables IRQs, and core 1 must call `flash_safe_execute_core_init()` ([pico_flash docs](https://picodocs.pinout.xyz/group__pico__flash.html)). The probe's CYW43 radio is driven by a PIO-based SPI in the SDK, and debugprobe hard-codes `pio0`, so the SWD program should be moved to a PIO block the radio does not use.

**Capture manifest generation (PC, Python).** Only variables with a fixed address can be sampled: `DW_TAG_variable` entries whose location is `DW_OP_addr`. DWARF "doesn't provide you with the means to read things, but does tell you where the things are" ([dwarf-discuss](https://lists.dwarfstd.org/pipermail/dwarf-discuss/2021-March/001986.html)). pyelftools walks CUs and DIEs and handles location lists ([pyelftools example](https://chromium.googlesource.com/chromiumos/third_party/pyelftools/+/master/examples/dwarf_decode_address.py), [pyelftools locationlists.py](https://sources.debian.org/data/main/p/python-pyelftools/0.32-1/elftools/dwarf/locationlists.py)). **[Inference]** The generator resolves type chains (typedef, const/volatile, struct members, enums, bitfields), includes function-statics, skips locals, and falls back to `.symtab` `STT_OBJECT` symbols when DWARF is missing. It reports "optimised out" rather than failing. For peripherals it parses the RP2040 SVD (Python `cmsis-svd` 0.6 or `svdsuite` ([cmsis-svd](https://pypi.org/project/cmsis-svd/), [svdsuite](https://pypi.org/project/svdsuite))) and emits only allowlisted registers. The output is a small binary manifest of `{id, addr, size, class/rate}` entries, sorted by address and merged into contiguous runs, plus a hash of the ELF (GNU build-id or SHA-256) and of the SVD. The probe never sees a symbol name.

**Storage and format (probe).** Pre-trigger capture lives in a RAM ring. A trigger freezes the pre-window, records a post-window, and commits the whole event to non-volatile storage. Onboard QSPI flash erases in 4096-byte sectors, programs 256-byte pages and endures at least 100K cycles on the original Pico's W25Q16JV ([J. Margolin](https://jmargolin.com/pico-projects/flash.htm)). The record format follows the Memfault coredump model: a header, then typed blocks of registers, memory regions and build ID ([Memfault docs](https://docs.memfault.com/docs/mcu/coredumps)). **[Inference]** Each 4 KB block carries magic, sequence number, a 64-bit probe timestamp, a block type (continuous / pre-trigger / post-trigger / event) and a CRC32. Records inside a block are `varint Δt, id, raw bytes`, written change-only with periodic keyframes, so any surviving block decodes on its own. Status records cover halted, locked-up, reset, SWD error and probe overrun.

**Decoding pipeline (PC, Python).** Stage one symbolises each sample. It splits register words into fields via SVD `<enumeratedValues>`, using the `read` usage set ([CMSIS-SVD enumeratedValues](https://siliconlabs.github.io/Gecko_SDK_Doc/CMSIS/SVD/html/group__svd__xml__enum__gr.html)), and maps enum variables through DWARF enumerators. Stage two runs small detectors (change, edge via XOR of `GPIO_IN`, threshold with hysteresis, deadband) that emit typed events to `events.jsonl`. Stage three renders YAML templates into `trail.txt` and writes timelines. For faults, stacked PC/LR are mapped to `file:line` with pyelftools or `addr2line`. The decoder also exports a CrashDebug dump, so the group can run `bt full` in GDB against the ELF ([CrashDebug](https://github.com/adamgreen/CrashDebug), [Memfault Interrupt](https://interrupt.memfault.com/blog/firmware-logs-stack-trace)).

## What makes it universal, and the target-profile layer

The box is universal across **firmware** by construction, and can be made universal across **chips** with one extra layer.

**Universal today.**

- **Any firmware, unchanged.** Nothing is compiled into the target: no logging library, no RTT buffer, no hooks. Any program's ELF is enough to record it.
- **All target knowledge comes from standard files.** Variable names, types and addresses come from DWARF, which any GCC/Clang build can emit. Peripheral names and fields come from the vendor SVD, which every Cortex-M vendor publishes. The probe only ever sees `{id, addr, size}` entries from the manifest, so a new program or board needs a new manifest, not new probe firmware.
- **Standard debug architecture.** SWD, the DP and the MEM-AP (ADIv5) are common to all Arm Cortex-M parts, so the same read loop works on an STM32, an nRF52 or an RP2350.

**Still RP2040-specific in the design above.**

- Multidrop TARGETSEL values (`0x01002927` / `0x11002927`) and the Rescue DP prohibition.
- The peripheral allowlist and the list of registers with read side effects.
- Timestamps taken from the RP2040 `TIMERAWH/TIMERAWL` registers.
- The assumption that DWT_PCSR exists. Most Cortex-M0+ parts lack it; M3/M4/M33 parts have it, plus SWO trace.
- ARMv6-M fault decoding, which has no CFSR/HFSR/MMFAR/BFAR. ARMv7-M and ARMv8-M parts name the fault cause in those registers.

**Proposal: a target profile.** **[Inference]** Move every chip-specific item into a per-chip profile file that the PC tool merges into the manifest. The probe firmware stays generic, and supporting a new chip means writing one profile.

| Profile field | RP2040 value | Example on another chip |
|---|---|---|
| Connection | SWD multidrop, core0 `0x01002927`, core1 `0x11002927`, forbid `0xF1002927` | Plain single-drop SWD (STM32F1) |
| Architecture | ARMv6-M (M0+), dual core | ARMv7-M (M3/M4) |
| Debug features | DWT_PCSR yes; cycle counter, ITM, SWO no; 4 BP / 2 WP per core | PCSR, DWT_CYCCNT, ITM, SWO yes; 6 BP / 4 WP |
| Fault decoder | Stacked frame + PC disassembly heuristic | CFSR/HFSR/MMFAR/BFAR decode |
| Timestamp source | `TIMERAWH/L` at 0x40054024/28, 1 µs | `DWT_CYCCNT` or the probe's own clock |
| Peripheral allowlist / denylist | GPIO_IN, PWM, ADC, UART regs listed in decision 7; deny FIFO_RD, TIMELR, UARTDR, ADC FIFO | Taken from that chip's SVD + its own denylist |
| Halt side effects | TIMER and watchdog pause on halt | Per-chip `DBGMCU` freeze bits |
| RAM regions | 0x20000000, 264 KB | Per memory map |
| Max SWD clock | 24 MHz | Per datasheet |

**How to demonstrate it in the course.** Record a second target, for example an STM32 "Blue Pill" or another Pico 2, using the same probe binary with only a new profile and manifest. If the trail and timeline come out correctly without reflashing the probe, the "universal" claim is shown rather than asserted. This is added as Phase 7 below.

## Twelve design decisions, each with a recommendation

| # | Decision | Options considered | Recommendation and reason |
|---|---|---|---|
| 1 | SWD engine | debugprobe PIO (MIT); yapicoprobe PIO; free-dap (BSD, bit-banged, bare-metal); Black Magic Probe | **debugprobe PIO + own ADIv5 layer.** It is Pico-SDK-native, builds for RP2350, and its licence is clear ([debugprobe](https://github.com/raspberrypi/debugprobe)). yapicoprobe is faster but its clone has no LICENSE file, so use it as reading material only ([yapicoprobe](https://github.com/rgrr/yapicoprobe)); free-dap is a readable protocol reference ([free-dap](https://github.com/ataradov/free-dap)) |
| 2 | Where symbols are resolved | On probe; on PC | **PC.** The probe stores IDs and raw bytes; this is how J-Scope and MCUViewer already work ([SEGGER KB](https://kb.segger.com/J-Scope), [MCUViewer](https://github.com/klonyyy/MCUViewer)) |
| 3 | Manifest delivery | Compiled-in header; file in flash via USB CDC/Wi-Fi | **Header in Phase 1, USB upload to a flash config area from Phase 3**, so the probe need not be reflashed for each target build |
| 4 | Core register capture | Periodic halts; watchpoint halts; halt on fault only | **Halt on fault only** via `VC_HARDERR`, which halts the core at HardFault entry ([TI SWCU193](https://ti.com/document-viewer/lit/html/SWCU193/GUID-20221130-SS0T-LTTD-HKTS-BP9GRCRJHXBH)); periodic halts freeze TIMER/watchdog |
| 5 | Continuous execution view | None; DWT_PCSR sampling | **PCSR sampling** in every fast frame; costs one read ([RP2040 datasheet](https://cdn.sparkfun.com/assets/b/2/6/7/2/rp2040-datasheet.pdf)) |
| 6 | Use of the 2 DWT watchpoints / 4 breakpoints | Unused; stack-guard watchpoint; state-change watchpoint | **Unused by default, optional "guard" mode.** On ARMv6-M a watchpoint can only halt the core ([TI SWCU193](https://ti.com/document-viewer/lit/html/SWCU193/GUID-20221130-SS0T-LTTD-HKTS-BP9GRCRJHXBH)), so every hit costs a full halt **[Inference]** |
| 7 | Peripheral selection | Sweep all SVD registers minus `readAction`; explicit allowlist | **Allowlist** (GPIO_IN, IO_BANK0 CTRL for used pins, PWM CSR/DIV/CTR/CC/TOP, ADC CS/RESULT, UART FR/IBRD/FBRD/LCR_H/CR/RIS), checked against SVD `readAction` and a denylist |
| 8 | Fault/reset detection | PC-in-handler heuristic; DHCSR polling | **Poll DHCSR** for S_HALT, S_LOCKUP, S_RESET_ST and S_RETIRE_ST ([TI SWCU193](https://ti.com/document-viewer/lit/html/SWCU193/GUID-20221130-SS0T-LTTD-HKTS-BP9GRCRJHXBH)); on reset read `WATCHDOG.REASON` and `CHIP_RESET` ([rp-pac](https://docs.embassy.dev/rp-pac/git/rp2040/vreg_and_chip_reset/regs/struct.ChipReset.html)) |
| 9 | Timestamps | Probe clock only; target TIMERAW only; both | **Both.** Read target `TIMERAWL` before and after each frame (no latching side effects ([RP2040 §4.6](https://xiao-seeed-rp2040-renode.readthedocs.io/en/latest/specification/rp2040-datasheet/06_chapter_4_peripherals/06_4.6_timer/))), plus the probe's 64-bit µs timer to reconstruct halt gaps |
| 10 | Non-volatile storage | Raw sector ring in onboard flash; littlefs; SD card; PSRAM board | **Raw CRC'd sector ring in flash for events; littlefs only for config/manifest; SD as an optional add-on for long continuous logs.** littlefs is power-safe but "SPIFFS will likely outperform littlefs on small memories" and writes commit only on sync ([littlefs README](https://www.gitlink.org.cn/mirrors/littlefs)); SD over SPI reaches 2.92 MiB/s write ([carlk3](https://github.com/carlk3/no-OS-FatFS-SD-SDIO-SPI-RPi-Pico)); the plain Pico 2 W is not among the PSRAM boards ([pico-sdk PSRAM commit](https://pigweed.googlesource.com/third_party/github/raspberrypi/pico-sdk/+/3193fae8973096e2034e8032363cb422c80fb122)) |
| 11 | On-probe compression | None; heatshrink; LZ4 | **None at first; change-only encoding instead.** Add heatshrink (<100 B RAM, ISC licence ([heatshrink](https://github.com/SocioPatterns/heatshrink))) per block only if flash fills too fast |
| 12 | Timeline viewer | Perfetto; VCD + GTKWave/Surfer; Plotly HTML; sigrok; Grafana | **Perfetto primary, VCD secondary, Plotly in the HTML report.** Perfetto handles instants, slices and counter tracks from Python ([Perfetto converting](https://perfetto.dev/docs/getting-started/converting)); pyvcd gives a logic-analyser view ([pyvcd](https://pyvcd.readthedocs.io/en/latest/vcd.writer.html)) that Surfer opens in the browser ([Surfer paper](https://ics.jku.at/files/2025CAV_Surfer.pdf)). sigrok only pays off for raw bus bits, and Grafana needs a database server |

Two choices deserve a defence against the obvious alternative. The first is halt-on-fault versus watchpoint triggers (decision 6). PicoReg 2's "watch" mode works on RP2040 only by forcing a break ([PicoReg 2](https://iosoft.blog/picoreg2)). **[Inference]** A write watchpoint halts on *every* write, even of an unchanged value, so a hot variable would turn the "non-intrusive" box into a stop-start debugger. Keeping watchpoints off by default protects the project's central claim. The second is the allowlist versus "SVD minus `readAction`" (decision 7). The SVD path looks more universal, but one missed side-effect register silently corrupts the system under test. An allowlist fails safe: the worst outcome is a register we forgot to record.

## Performance budget: about 1 kHz for 50 variables at 10 MHz

Every number in this section except the inputs is an **[Estimate]**. The sourced inputs are these. The RP2040's recommended maximum SWD clock is 24 MHz ([RP2040 datasheet](https://cdn.sparkfun.com/assets/b/2/6/7/2/rp2040-datasheet.pdf)). yapicoprobe caps RP2040 targets at 25 MHz, 24 usable, with a default of 8 MHz ([yapicoprobe](https://www.Github.com/rgrr/yapicoprobe)). PicoReg 2 recommends ~10 MHz on cables of at most ~15 cm with a good ground ([PicoReg 2](https://iosoft.blog/picoreg2)). After optimisation, yapicoprobe measured four command sequences at ~18 µs at 15 MHz ([yapicoprobe optimizations](https://github.com/rgrr/yapicoprobe)). That is about 4.5 µs per transaction against an ideal ~3 µs, i.e. **~1.5× protocol overhead**. A 32-bit SWD transaction is ~46 clocks plus idle cycles. We plan with 10 MHz on jumper wires and treat 24 MHz as a stretch goal for a short soldered harness.

| Quantity | Basis | 10 MHz (plan) | 24 MHz (stretch) |
|---|---|---|---|
| One transaction (ideal → practical, ×1.5) | ~48 clocks | 4.8 → ~7 µs | 2.0 → ~3 µs |
| Fast frame: 50 globals in ~10 address runs + DHCSR + PCSR + 2× TIMERAWL | ~70 transactions | ~0.5 ms → max ~2 kHz | ~0.21 ms → max ~4.7 kHz |
| **Recommended fast rate** | ~50 % of link at 10 MHz | **1 kHz** | 2–4 kHz |
| Slow (peripheral) frame: GPIO_IN, ~10 GPIO CTRL, 8 PWM slices × 5 regs, ADC, 2 UARTs | ~90 transactions | ~0.63 ms; at **100 Hz** uses ~6 % of link | ~0.27 ms |
| Core1 DHCSR check (line reset + TARGETSEL + DPIDR + read, then switch back) | ~10 transactions + resets | ~0.1 ms; at 100 Hz ~1 % | <0.05 ms |
| Halt-read-resume for 17 core registers | ~50+ transactions | ~0.35 ms target-time freeze | ~0.15 ms |
| Fault capture: registers + 8-word stacked frame + 4 KB of stack + SCS | ~1,100 transactions | ~8 ms | ~3.5 ms |
| Full 264 KB SRAM snapshot (1 transaction/word, TAR re-write per KB) | ~67,800 transactions | **~0.47 s** | ~0.2 s |
| Raw data rate (1 kHz × 216 B + 100 Hz × 336 B) | — | ~250 kB/s | — |
| 256 KB RAM pre-trigger ring holds | raw / change-only at 5–20× | ~1 s / ~5–20 s | — |

The numbers point one way. **Storage, not SWD, is the bottleneck**, as one research note concluded independently. **[Estimate]** Raw continuous logging at ~250 kB/s cannot go to onboard flash. Typical NOR figures are ~45 ms per 4 KB sector erase plus ~0.4 ms per 256-byte page, but these are unverified for the Pico 2 W's flash part, and they put sustained writes near ~75 kB/s, with every erase stalling XIP. Hence the split. The full-rate stream lives only in the RAM pre-trigger ring. The flash ring receives triggered events and an optional decimated continuous stream (e.g. 10 Hz keyframes). An SD card (2.92 MiB/s over SPI, sourced above) takes the full-rate continuous stream if the group wants hours of recording. The change-only compression ratio (5–20×) is a guess for a PicoBricks app that mostly waits for input, and Phase 2 should measure it. The RP2350's 520 KB SRAM, which makes the 256 KB ring affordable, is general knowledge not verified in our sources. Data that is not atomic is also part of the budget: at 10 MHz a 50-variable frame is spread over ~0.5 ms. The decoder must treat a frame as a time *interval* bounded by the two TIMERAWL reads, and read multi-word values twice and compare to detect tearing.

For calibration, a PC-hosted tool polling through a CMSIS-DAP probe reaches about 1,000 reads per second ([PicoReg 2](https://iosoft.blog/picoreg2)), and STMViewer topped out at about 1 kHz ([Interrupt: STMViewer](https://interrupt.memfault.com/blog/stm-viewer-debug)). A standalone probe has no USB round-trip per packet, so it should beat this by roughly 50–100× in *words* per second. If Phase 0 measures under ~50k words/s at 10 MHz, the PIO loop has a bug, not a physics limit.

|---|---|---|

| PlatformIO ELF lacks DWARF, or `-g` changes code | Medium / high | Add `-g` to release `build_flags`, verify `.text` hash equality; `.symtab` fallback; report "optimised out" |

| Halt side effects (timer/watchdog freeze) on fault capture distort post-fault behaviour | Certain when triggered / low | Halt only on fault; log probe wall-clock across the halt; record the freeze duration as an event |
| SWD signal integrity on jumper wires | Medium / medium | Start at 1–4 MHz, step up; ≤15 cm leads with ground ([PicoReg 2](https://iosoft.blog/picoreg2)); count WAIT/FAULT ACKs as health metric |

## Validation: scripted stimulus versus decoded trail

No published method exists for validating an SWD-polled recorder, so the validation plan is our own design built from standard practice **[Inference]**. A **test firmware** on the PicoBricks board runs a known script. It produces a GPIO pulse-width ladder (100 µs … 100 ms), periodic toggles, a PWM sweep in 10 % steps every 500 ms, potentiometer/ADC threshold crossings, enum state changes and, finally, a deliberate fault at a known `file:line`. Ground truth comes from an **independent logic analyser** (an fx2-class sigrok device on the same pins), because a target-side log would share the system under test's errors. Clocks are aligned on sync toggles at the start and end with a linear offset-and-drift fit. The decoded `events.jsonl` is matched to the truth by nearest neighbour within ±2 sample periods. The plan reports recall (missed events), precision (spurious events), timing error (median, p95, max) and the achieved sample rate with dropped-frame count over a long run. The pulse ladder yields a **detection curve**: for a pulse of width w shorter than the period T, detection probability is about w/T. This turns "we sample at 1 kHz" into an empirical claim. PWM duty and pin-function values are read from registers rather than measured, so they must match *exactly*. Intrusiveness gets its own test: run the target firmware with and without the probe attached and compare a timing-sensitive output (e.g. a PWM-generated waveform period or a loop-counter rate) to show the difference is within measurement noise. Finally, a stored golden `events.jsonl` lets the decoder be regression-tested on recorded captures without hardware.

The EDR analogy gives the report a vocabulary for this. US rules for vehicle event data recorders moved pre-crash capture "from 5 seconds of pre-crash data at a frequency of 2 Hz to 20 seconds of pre-crash data at a frequency of 10 Hz", with a fixed list of named elements ([Federal Register 2024-29862](https://www.govinfo.gov/content/pkg/FR-2024-12-18/html/2024-29862.htm)). The black box can be specified in exactly those terms, e.g. "last 10 s at 1 kHz of 50 signals before HardFault". That makes the sample-rate versus memory trade-off explicit and testable.

## Conclusion

The project's novelty is not the SWD reading itself, which J-Scope, MCUViewer and PicoReg already do from a PC. It is the move to a self-contained, triggered recorder whose central claim, non-intrusiveness, can be *measured* rather than asserted. The design therefore treats intrusiveness as a declared, per-recording level (passive read, debug config, halt) instead of a yes/no property. The decisive RP2040 details make this both possible and delicate. Bus priority makes reads nearly free, and PCSR gives an execution trace without halting. But a single halt freezes the timer and watchdog, and a single careless read can pop a FIFO.

The budget also inverts the usual worry. The SWD link at 10 MHz comfortably outpaces what the probe can persist, so effort should go into the RAM pre-trigger ring, change-only encoding and the CRC'd flash ring, not into squeezing the PIO loop toward 24 MHz. If Phase 0 confirms the estimates, Group 7 can specify the box in EDR terms, for example "N seconds at 1 kHz of M signals before a HardFault, with timestamps accurate to one sample period". Those are numbers the validation suite can prove and a grader can check.
